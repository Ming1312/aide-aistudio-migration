# 07　已知限制與未來發展方向

> 本專案已進入結案收尾：以下「未來發展」**不在本次交付範圍**，不是承諾，只是指出證據顯示最值得做的方向。

## 1　已知限制

### 1.1 資料與研究

| 限制 | 影響 |
|---|---|
| **沒有獨立的盲測資料**：資料在 Phase 1～5.7 被反覆檢視，所有結果是 walk-forward 回測 | 結果只能稱「探索性」；**沒有任何模型或偵測器是 Validated**；不能宣稱泛化到未知季節或場域 |
| **資料期間短**：羊舍只有 36 天、單一夏季；其他場域 1～4 個月；育成北側只有 387 列 | 羊舍高 THI 獨立事件只有 21～31 段；北側不建模；多數結論的信賴區間很寬 |
| **沒有任何設備故障標籤** | 異常只能稱「候選事件」；Predictive Maintenance Readiness 為 Insufficient Evidence；偵測準確率無法在真實資料上計算 |
| **單位未確認、時間戳無時區、感測值「何時可取得」未確認** | 單位多為推測；as-of 假設時間戳＝可取得時間 |
| **風險門檻 THI 84 是候選門檻**（83／84／85 做過敏感度分析） | 不是資料提供者確認的熱緊迫標準；所有風險等級都附「候選、未確認」 |
| **模型主要學到日夜週期**：羊舍 HGB 相對「同小時平均變化」只好約 5%，區間含 0 | 不能說模型「看懂了感測器的因果」；額外感測器、風扇、捲簾特徵沒有可辨識的增益 |
| **警報線不穩定**：只靠 5 天內層資料選，各折實際 FPR 從 0.03 到 0.25 | 目前最大的實務風險；比換模型更重要 |
| **警報能力無法顯著優於「只看時段」的氣候機率基準** | 不能宣稱模型式警報比簡單作法顯著好；高 THI 漏報下降是用誤報增加換來的 |
| **預測區間不均勻**：下午時段覆蓋率偏低（0.83）；105 個任務中 42 個 `UNCERTAINTY_NOT_VALIDATED` | 區間是參考，不是保證 |
| **感測器可信度、守門、異常偵測的數字大多來自合成資料** | 只描述偵測器在合成產生器上的表現；守門對雜訊變大與斷線仍漏掉 35%／42%；真實改變被誤攔 10% |
| **資料漂移旗標過於敏感**（78/90 被標為漂移候選，其中 44 沒有表現退化） | 漂移旗標只是提示，不是重訓依據 |
| **展示情境是挑選過的**（D1～D5 合成故事） | 不是偵測器效能證明；D3（漂移初期）七場域中有 4 個如實漏報 |
| **資料授權只有使用者聲明**（`user_attestation_only`） | 沒有書面同意或標準授權；聲明範圍是本競賽專題，長期公開散布或商業用途不明確；GitHub repo 必須維持 private |

### 1.2 系統與部署

| 限制 | 影響 |
|---|---|
| **沒有連接真實現場設備或即時資料**；即時預測資料流是合成的 | 「自動更新」展示的是流程，不是現場監測 |
| **不控制任何設備**；不宣稱風扇／捲簾降 THI 的效果；人工決策一律是模擬紀錄 | 決策輔助只輸出「檢查／確認／通知」類建議 |
| **F12（未修正）**：唯讀部署下管理者按寫入顯示 502「引擎憑證設定有誤」 | 非阻擋；真正原因是引擎停用寫入；最小修正已備好但未套用、未實測 |
| **模型維護、羊舍人工決策與審查的寫入功能停用** | 介面標示停用；引擎端寫入端點存在，但經 App 的管理者流程未實測 |
| **Quick Tunnel**：臨時公開網址、Cloudflare 終止 TLS（看得到 `X-API-Key`）、網址每次改變、無可用性保證、同時 200 個處理中請求上限、所有人共用限流額度 | 只適合展示與測試；金鑰用完即換 |
| **引擎在使用者電腦上**：電腦關機、休眠或斷網，AI Studio App 就連不到引擎 | 展示前要先確認；App 會降級為離線模式而不是當機 |
| **Gemini 未實測**：沒有設定金鑰，只驗證規則式降級 | 白話改寫的真實品質未知；Gemini 只改寫文字，不產生任何建議 |
| **平台觀察**：引擎離線時直接 fetch 狀態端點回 200 HTML | UI 正確顯示離線；原因未深究 |
| **版本庫長時間成長未驗證**；不自動清理 | 合成資料流每輪每場域新增一版；`status.sh` 提供磁碟與大小警告 |
| **未驗證**：區網其他裝置連線、電腦重開機後自動重啟、Tunnel 4 小時自動關閉的實際行為、負載／壓力測試、真實 TLS／網域、`copy_key.py`（GTK 剪貼簿）在本次驗收沒有使用 | 都不在展示路徑上 |
| **Docker 映像約 569 MB**；Compose ≥ 2.24 才支援覆蓋檔 | 安裝需求 |

## 2　未來發展方向（依證據排序，非承諾）

1. **前瞻驗證（最重要）**：取得 2026-08-13 之後的新資料，**不重訓**，直接用既有模型預測並與實際值比對（羊舍的指令與流程已在原研究專案 README 準備好）。只有這一步能把「探索性」升級。
2. **確認資料與門檻**：向資料提供者確認單位、時區、感測值可取得時間、THI 熱緊迫門檻與設備狀態碼；取得資料授權的書面文件。這是讓 `formal_risk` 擴及其他場域的前提（登錄表已寫明升級條件）。
3. **取得故障／維修標籤**：沒有標籤就無法評估異常偵測；可從維護紀錄或人工標註建立最小標籤集，再重新評估候選偵測器。
4. **更長、跨季節的資料**：LSTM 與更複雜模型目前都受資料量限制；樹模型也隨資料量改善（HGB 67/90 任務）。育成北側需要累積連續資料才可能建模。
5. **補外部領先變數**：日射、雲量、室外溫度。Phase 2.6 指出沒有這些變數，快速升溫的提早偵測有結構性上限。
6. **穩定警報線**：以更長的校正資料或分層校正降低跨折 FPR 波動；先於換模型。
7. **補完寫入階段（M4／M5）並套用 F12 修正**：模型重訓／啟用／回復、人工決策紀錄、審查紀錄；管理者流程在可信環境下實測。
8. **正式部署**：自己的網域與 named tunnel／反向代理與認證，取代 Quick Tunnel；金鑰管理（Secret Manager）；監控與備份；容量與長時間成長測試。（這會涉及費用與帳號，需使用者另行決定。）
9. **真實 Gemini 驗證**：在 Free Tier 下做小規模實測，核對白話改寫是否忠實於規則層（核對機制已有單元測試）。
10. **與現場營運對接**：先以人工確認流程試用，收集使用者回饋與誤報成本，再談自動化；任何控制設備的功能需要另行的安全評估。
