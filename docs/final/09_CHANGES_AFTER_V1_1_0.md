## 1　「場域決策」五頁：七個場域一視同仁

原本「風險評估／處置決策／異常診斷／AI 預測／歷史回放」五頁只在羊舍出現，且羊舍用一套凍結的正式引擎輸出。依使用者要求「不要把羊舍跟其他做區別」，現在**七個場域用同一套程式、同一種方法、同一版型、同一種說法**（側邊欄「場域決策（假定門檻）」；只在真實資料模式）：回放時點選擇器（as_of，136～168 個起點）、現況／點預測（含 90% 區間）／越過門檻機率與風險等級／感測器可信度與簡單基準四張卡、模型輸出原因、帶區間的回放圖；AI 預測頁多六方法比較表，歷史回放頁多混淆矩陣摘要；異常診斷與處置決策頁也相同。頁面代號改為中性的 `decision_*`（原 `sheep_*`）。

| 場域 | 決策目標（感測器） | 方向 | 注意線 | 警戒線 | 備註 |
|---|---|---|---|---|---|
| 羊舍 | 成羊區 THI | 越高越危險 | 84（候選門檻，沿用研究的分析門檻） | 86（假定） | 與其他場域同一種處理 |
| 專家系統 C22 | DO1 即時值（mg/L） | 越低越危險 | 4.0 | 3.5 | 養殖慣例的緊迫線更低（約 3），但回放視窗最小 3.25，為了示範有事件而調高 |
| 三爺宮溪 | 電池電量（%） | 越低越危險 | 90 | 80 | 水質預測可信度低，改以供電健康為風險 |
| 工地微氣候 | 噪音（dB(A)） | 越高越危險 | 65 | 75 | 噪音三個時距皆為 ML 候選 |
| 東北角 | PM2.5（µg/m³） | 越高越危險 | 15 | 25 | 常見標準約 35，但視窗最大 28.3，故調低 |
| 育成一廠 | TEMP（°C） | 越高越危險 | 30 | 33 | TEMP 為 ML 候選 |
| 育成一廠北側 | 溫度（°C） | 越高越危險 | 30 | 33 | 資料很不完整（387 列、涵蓋 17.6%）、沒有預計算預測：改用瀏覽器內的簡易基準預測（見 §2g）；異常診斷照常提供 |

**（此段已被 §2h 取代：現在預設由歷史資料計算）所有門檻原本是假定值**（依使用者 2026-11-26 的決定「候選門檻先用假定的值」）：沒有任何一個經資料提供者確認，也沒有故障標籤可驗證；部分為了讓回放視窗出現事件而偏離一般慣例，畫面逐項說明；使用者可在畫面上改注意線與警戒線（只存在分頁記憶體）。

**這個改動拿掉了什麼（必須知道）**：羊舍原本的「Phase 2.6 凍結正式引擎」輸出頁（HGB 點預測＋CQR 預測區間＋ProbLinQ 超標機率＋警報線＋視窗風險）**不再出現在 App 的導覽裡**，羊舍現在跟其他場域一樣用下面的「研究預測＋滾動區間」方法。`SheepDecisionPages.tsx` 已從這個分支刪除（仍在 `release/aide-v1.1.0` 與 `main` 的歷史裡可取回）；引擎端的 `/v1/formal/sheep-thi` 與預計算的 `formal_sheep.json` 沒有動。羊舍正式模型的研究結果（區間覆蓋 0.900、漏報 0.307→0.078 等）仍記錄在研究文件裡，但 App 不再展示它。另外「決策輔助」頁的「風險決策」層仍然由引擎端的登錄決定（目前只有羊舍登錄了風險決策引擎輸出），該頁的版型已改成七個場域一致，沒有登錄的場域顯示原因並指向「場域決策」。

**輸出怎麼算（`src/lib/replayEngine.ts`；七個場域相同）**：**引擎預先算好的研究預測**（預設用該任務的最佳基準，可改選六種方法）加上下列純因果計算（起點 t 只用目標時間 ≤ t 的真值）：
- 區間：split-conformal，最近 72 筆已抵達殘差，名目 90%（校正資料 < 24 筆時不顯示區間與機率）；
- 越過門檻機率：同一批殘差的經驗分布（平移到點預測上，Laplace 平滑）；
- 警報線：只用起點當下已抵達的歷史事件，以召回率 0.9 為目標選出（事件 < 3 筆用預設 0.15）；
- 風險等級：low／elevated／high，另附原因；
- 感測器可信度：連續 6 小時相同值，或起點前 24 小時內該感測器的卡值／漂移／斷線候選事件 → unreliable／「先處理資料」；
- 回放摘要：混淆矩陣、召回、誤報率、精確率、警報段數，與「現值已超標才警報」的反應式規則並排。

**誠實揭露**：以召回率 0.9 為目標的警報線會換來高誤報（例如育成一廠 TEMP 3 小時：預測式召回 90%、誤報率 59%、精確率 30%；反應式召回 70%、誤報率 10%、精確率 66%）——與羊舍 Phase 2.5 的取捨同型。樣本只有 136～168 個起點、事件很少、門檻是假定的：這些比例只是流程示範，**不是效能證據**。

程式：`src/lib/replayEngine.ts`、`src/lib/candidateRisk.ts`（門檻政策與分類）、`src/pages/DomainDecisionPages.tsx`。測試：`replayEngine.test.ts`（7 項，含「竄改起點之後的真值不改變該起點輸出」的因果性測試）、`candidateRisk.test.ts`（10 項）。

## 2e　三個角色＋即時預測串接電腦上的引擎（2026-11-27）

**三個角色**（權限表在 `contracts/permissions.ts`，前端與伺服器共用；登入視窗會顯示同一張表）：

| 能力 | 訪客 | 員工 | 管理員 |
|---|---|---|---|
| 查看、AI 問答 | ✓ | ✓ | ✓ |
| 記錄決策 | — | ✓ | ✓ |
| 資料匯入（含伺服器代取檔案） | — | ✓ | ✓ |
| 看引擎連線狀態 | — | ✓ | ✓ |
| 改風險門檻 | — | — | ✓ |
| 管理狀態面板 | — | — | ✓ |
| 引擎寫入 | — | — | ✓（只有正式管理員；伺服器強制） |

- 訪客＝不登入。員工與管理員都在同一個登入視窗以「帳號＋密碼」登入。
- **公開的展示帳號**（寫在程式與畫面上，所以只用於展示）：員工 `staff`／`aide-staff`；管理員（展示）`demo`／`aide-demo`。展示管理員有管理員的畫面權限，但**伺服器永遠不替它寫入引擎**。

- 伺服器端實際強制的：`/api/import/fetch` 需員工以上（否則 403）、`/api/admin/status` 需管理員、引擎寫入端點僅正式管理員。**畫面上的鎖（記錄決策、匯入、門檻）是前端限制**：匯入資料與決策紀錄本來就只存在使用者自己的瀏覽器，不是伺服器端資料。
- 測試：`adminAuth.test.ts` +3、`routes.test.ts` +2（含員工不能寫引擎、展示提示只在沒有正式帳號時出現）。

**即時預測串接你電腦上的引擎**：App 每 30 秒問 `/api/health`；引擎連上時改讀各場域 `/api/live/<id>/forecast`、`/status`（唯讀），總覽與決策改用引擎的即時預測。優先順序：**匯入資料 ＞ 引擎即時 ＞ 離線預計算**，每張卡片標示來源。引擎的資料流是**模擬（合成）資料**，畫面標示「引擎・模擬流」。引擎即時輸出沒有區間與機率，所以引擎來源的卡片只有點預測與門檻比較；資料過時或有旗標時顯示「先確認資料」。

啟動方式（由你執行；我沒有啟動 Docker 或引擎）：`bash demo_kit/start_local.sh`，再 `bash scripts/dev_with_engine.sh`（從 `~/aide-demo/state/demo.env` 讀金鑰放進 Node 行程環境，不顯示、不寫檔；引擎網址固定 `http://127.0.0.1:8088`）。連線狀態在「設定 → 引擎連線」（員工以上可見）。

**驗證與限制**：用一個本機假引擎（`GET /health`、`/v1/live/*`，只回固定數字，不是真引擎）端到端試過：總覽兩個場域改成「引擎・模擬流」並依門檻判為危險／安全、30 秒輪詢更新、決策頁圖用引擎歷史、訪客／員工／管理員（展示）三種畫面。**沒有連到真正的 Python 引擎**（要你啟動 Docker），所以真引擎的實際欄位與數值未驗證；引擎欄位對應沿用既有的 `liveAdapter`（v1.1.0 時對真引擎驗過）。

## 2f　整份 Google 試算表一次匯入（2026-11-27）

「匯入」頁新增預設分頁「整份試算表」：貼一次試算表網址 → 「讀取所有工作表」→ 伺服器從 `htmlview` 頁面列出全部工作表（`GET /api/import/sheet-tabs`，員工以上）→ 逐張下載 CSV → **依欄位自動判斷屬於哪個場域**（與原始表頭完全相同的欄位權重最高）→ 表格列出「工作表／匯入到／列數／時間範圍」，可改場域或取消勾選 → 「全部匯入」。每張工作表各存成一個來源，之後可一起自動更新（手動／每 1、5、15、60 分鐘）；同網址同場域重複匯入不會重複新增來源。

用你提供的試算表實測（7 張工作表，全部自動對到正確場域）：三爺宮溪 2,881 列、專家系統 2,698、工地微氣候 2,219、東北角 2,026、羊舍 871、育成一廠 2,204、育成一廠北側 387，共 13,286 列；欄位全數對應。為了讀這份試算表，解析器另外學會：日期＋小時兩欄、`2026/1/1` 不補零的日期、表頭前的說明列（工地那張有兩列圖例）。

**預測不會因此改變**：這份試算表的時間範圍與 App 內建資料相同（沒有更新的列），所以總覽仍用預計算的研究預測。規則是「匯入資料比原始資料更新時才改用匯入資料做預測」，避免用較簡單的方法取代研究預測。試算表之後新增的列（超過內建資料結尾，且該場域有 ≥72 小時歷史）才會讓卡片改成「匯入資料」並以簡易基準預測更新。

## 2g　育成一廠北側照常分析；資料可選日期起點（2026-11-27）

**育成一廠北側不再因資料不完整而被排除**：它現在跟其他場域一樣有風險政策（溫度，注意 30／警戒 33，假定值），總覽、決策、AI 問答都會分析。因為沒有預計算的研究預測，改用瀏覽器內的**簡易基準預測**（持續性，同一套因果區間與機率引擎）。三處處理：
- 北側最後 16 小時（2026-08-31）整列歸零（偵測器標為「整列歸零（斷電／斷線）」），這段視為缺值略過，分析依**最後有效資料**（2026-06-25 18:00，溫度 24.2 °C）；
- 卡片標「簡易預測・資料不完整」，決策頁顯示提醒：只有 387 列、涵蓋 17.6%、已略過 16 列、分析時點；AI 分析的事實清單也帶這段；
- 這是研究預測的替代品，**不是**有驗證的預測；資料來源停在 6 月底，所以「現在」其實是兩個月前的狀態。

**資料頁可選日期範圍**：除了 3／7／30 天／全部，新增「起點」「終點」日期欄（限制在資料範圍內）；選了日期就不再套用快捷範圍，「清除」可回到 7 天；選到沒有資料的日期會顯示資料範圍。「加入預測」跟著日期範圍。

## 2h　風險門檻改為「由歷史資料計算」，管理員仍可調整（2026-11-27）

**取代 §1 表格裡的假定值**：門檻不再是我假定的數字，改由各場域政策感測器的**歷史資料百分位**算出。
- 注意＝第 90 百分位、警戒＝第 97.5 百分位；越低越危險的感測器（專家系統 DO1、三爺宮溪電池電量）取對稱的下尾（P10／P2.5）。
- 略過偵測器標出的「整列歸零（斷電／斷線）」時段（北側 16 列）。樣本少於 48 筆或百分位不合法（需 50～99，且警戒 ≥ 注意）時不計算，退回程式內的假定值。
- **優先順序：管理員調整 ＞ 歷史計算 ＞ 假定值**；每張卡片與決策頁標示來源（歷史百分位／管理員調整／假定值）。
- 預先算好的表：`public/data/real_public/precomputed/thresholds.json`（`npx tsx tools/build_thresholds.mts` 產生；測試會檢查它沒有過期）。**匯入新資料後**，該場域改用「原始＋匯入」的資料在瀏覽器內精確重算。
- 管理員（含展示管理員）在「設定 → 風險門檻」可以：改全域百分位（預設 P90／P97.5，可改成別的）、逐場域直接改數字（顯示「管理員調整（歷史計算：x／y）」）、一鍵「重設為歷史計算」、「恢復 P90／P97.5」。員工與訪客只能看。調整存在使用者自己的瀏覽器。

結果範例（預設 P90／P97.5）：羊舍 THI 86／87.1、專家系統 DO1 2.85／2.39、三爺宮溪電量 94／88、工地噪音 60.6／68.6、東北角 PM2.5 22／30.4、育成一廠 TEMP 33.3／34.8、北側溫度 29.3／30.6。

**必須知道的限制**
- 百分位門檻說的是「統計上多罕見」（歷史上約有 10%／2.5% 的時間比它更極端），**不是安全標準**，也不是資料提供者確認的值；它會讓「歷史上常發生的偏高值」被視為正常（例如：原本假定值會判危險的專家系統 DO1 3.3 mg/L，在這份資料的 P10＝2.85 下是安全）。
- 整段歷史都用來算門檻，對歷史資料本身是樣本內的結果；歷史資料很短的場域（羊舍 871 筆、北側 354 筆）門檻不穩。
- 以格點內插：百分位介於預先算好的 1%～99% 格點之間時是近似值；匯入資料後的重算是精確的。
