# 01　成果說明：AIDE 智慧環境監測與決策平台

> 提供給指導老師與競賽評審。所有數字來自既有研究與實測證據（出處見 [03](03_MODELS_RESEARCH_AND_VALIDATION.md) 與 [06](06_FINAL_ACCEPTANCE_REPORT.md)），沒有重新訓練任何模型。**合成資料流不是連接真實現場設備；所有預測結果是探索性回測，沒有獨立盲測。**

## 1　研究動機

環境感測（畜牧、水質、微氣候、空氣品質）每小時都在產生資料，但現場管理者常常得不到三個問題的答案：**這筆資料可靠嗎？哪個場域現在需要處理？系統的建議有什麼依據？** 感測器卡值、漂移、斷線時，直接用資料訓練或預測，結果看似精確卻不可信；而單純追求更複雜的模型，在資料只有幾十天到幾個月時，常常沒有可辨識的好處。

本專題使用 2026 全國 AI 專題創意競賽提供的 JNC（銘祥科技）AIoT 感測資料（七個場域），目標是做出**誠實、可追溯、由人決策**的預測與決策輔助流程，而不是單一模型的分數。

## 2　問題定義

1. **預測**：在沒有任何設備故障標籤、資料期間很短的條件下，能否可靠地預測未來 1／3／6 小時的感測值？（主案例：羊舍成羊區 THI 3 小時後。）
2. **風險感知**：預測是否附帶不確定度與可信度？能否在「漏報」與「誤報」之間給出透明的取捨？
3. **資料品質與異常**：沒有故障標籤時，如何把「資料有問題」「疑似感測器漂移」「環境本來就變了」分開，並且不把候選異常說成故障？
4. **資料更新與模型維護**：新資料進來時，系統能否**先確認資料可靠再談預測**，並防止把故障學進模型？
5. **決策輔助**：七個場域是否都能得到有證據、有限制、不越權的建議？

## 3　創新性（如實定位）

本專題的貢獻主要在**研究流程與系統工程的嚴謹度**，不是提出新的演算法，也不宣稱超越現有方法：

| 面向 | 做法 |
|---|---|
| **評估協定** | 先寫規則再看結果；時間序列擴張視窗＋隔離區；洩漏稽核（含「故意放洩漏要抓得到」的自我測試）；每個 skill 標明基準；區塊 bootstrap；事前宣告的保留標準，**負面結果照實保留**（例如沒有任何改良通過，正式模型不替換） |
| **風險感知預測** | 感測器可信度模組＋CQR 預測區間＋超標機率＋風險等級，每項輸出標示「候選門檻、未確認」 |
| **資料先於模型的守門** | 感測器疑似故障時，建議改為「先處理資料」並擋下重訓；覆寫需填原因並寫入事件紀錄 |
| **三層決策輔助** | 一般建議／需人工確認的異常／正式風險決策；每項帶證據編號、可信程度、限制；規則層硬性禁止創造門檻、下故障結論、產生控制指令；LLM 只改寫文字，核對失敗改回規則層原文 |
| **真實與合成分離** | 真實資料與合成資料在檔案、API、介面三處分開標示；展示情境與真值分開；預測不得拿預計算結果冒充即時結果 |
| **可重現與可部署** | 版本固定（SHA-256）、Docker／Caddy 隔離驗收（CI）、唯讀引擎、離線降級、一鍵啟動／停止的展示套件，**全程零新增費用** |

## 4　技術方法（摘要，細節見 03）

- **預測**：HistGradientBoosting、XGBoost、Ridge 與基準（持續性、昨天同時刻、同小時平均變化、移動平均、線性自迴歸）並排比較；羊舍 THI 的預測目標為變化量。
- **不確定度**：分位數回歸與 CQR（Conformalized Quantile Regression）；超標機率與警報線。
- **異常偵測**：資料品質規則（卡值、缺值、斷線、歸零）＋殘差／CUSUM／與其他感測器不一致的統計偵測，**每個場域各自校準**；環境變化（被其他感測器解釋）不當作故障。
- **模型維護**：學習曲線、滾動起點、擴張 vs 滑動視窗、漂移分析、Champion–Challenger，皆為探索性。
- **系統**：Python FastAPI 引擎（唯讀）＋Caddy；React／Node（AI Studio Build Mode 產生）代理引擎並保管金鑰。

## 5　實驗結果（主要數字）

**羊舍 THI 3 小時預測**（36 天，Holdout 180 筆，MAE 單位 THI）

| 方法 | MAE |
|---|---|
| 持續性 | 1.493 |
| 昨天同時刻 | 1.241 |
| 同小時平均變化 | 0.975 |
| HGB | 0.924 |
| XGBoost | 0.902 |

- 模型明顯贏過持續性與昨天同時刻（對後者 skill +0.255／+0.273），但**相對「同小時平均變化」只好約 5%，區間含 0——主要學到日夜週期**。
- 風險感知：預測區間覆蓋率 0.865 → **0.900**；高 THI 漏報率 0.307 → **0.078**，代價是誤報率 0.093 → 0.261。**無法證明模型式警報顯著優於「只看時段」的簡單警報。**
- LSTM、日夜基準＋殘差、3 小時最高值模型：**都沒有通過事先宣告的標準**，正式模型維持不變。
- 其他場域（7 個預測任務）：XGBoost 贏 2、HGB 贏 1、分不出 4，平均相對差約 0。
- 通用基準研究（105 個任務）：只有 **23%** 的機器學習候選達到預先登記的勝出條件，其餘保留簡單基準。

**異常偵測與守門（全部為合成資料）**：留存 1,120 批次，v2 偵測器 precision 0.63、正常資料 FPR 1.6%、資料品質 recall 0.93、異常訊號 recall 0.67（v1：0.22、17.6%、0.65、0.72——**訊號 recall 略降；v1 的高 recall 有一部分是靠大量警報換來的**）。守門攔下 84.3% 的故障情境（建議重訓 66.3% → 11.0%），但誤攔 10% 的真實改變。**這些數字不是真實現場的故障辨識能力。**

**工程驗證**：AI Studio App `tsc` 0 錯誤、63/63 單元測試、Vite build 成功；原研究平台 1,606 項回歸測試通過；Docker／Caddy 於 GitHub Actions 隔離驗收 15 步全過；AI Studio→Cloudflare Tunnel→Caddy→引擎的遠端整合實測通過（七場域、自動更新、離線降級）。

## 6　系統功能

七場域真實資料總覽與探索；六個有模型的場域各 15 組（5 感測器 × 1／3／6 小時）的**合成資料流上的即時預測與自動更新**；七場域決策輔助（三層、證據可追溯）；合成資料更新展示（環境改變、感測器漂移、卡值與斷線，以及守門擋下重訓）；羊舍歷史回放式風險決策；引擎離線時誠實降級。育成一廠北側因資料不足（只有 17% 小時有讀值）依政策**不建模**。

## 7　實際應用價值

- **把「資料可靠嗎」放在預測之前**：感測器卡值、漂移、斷線會被分開標示，並阻止把故障學進模型——這對只有短期資料、沒有故障標籤的現場特別重要。
- **可信的取捨而不是單一分數**：預測區間、漏報／誤報的代價、候選門檻與限制都攤開，由人決定。
- **簡單方法優先的證據**：在多數任務上簡單基準已經夠好，降低導入複雜模型的成本與風險。
- **可低成本重現與展示**：整套系統可在一台一般電腦上以 Docker 啟動，免費 Tunnel 連到雲端介面，沒有任何付費資源。
- 價值屬於**輔助人工檢查與決策的原型**；尚未在真實現場閉環驗證。

## 8　限制（必須同時閱讀）

1. 沒有獨立盲測資料；所有結果是探索性回測；沒有任何模型或偵測器稱 Validated；羊舍只有單一夏季 36 天。
2. 沒有設備故障標籤；異常一律是「候選事件，不是故障判定」；合成資料上的偵測數字不等於真實能力。
3. 風險門檻 THI 84 是候選分析門檻，單位、時區未經資料提供者確認。
4. 即時資料流是合成的，**沒有連接任何真實現場設備**；系統不控制任何設備，不宣稱降低 THI 的效果。
5. 已知問題 F12（唯讀部署下管理者寫入顯示誤導訊息，非阻擋）；寫入類功能（模型重訓／啟用、人工決策紀錄）未開放；真實 Gemini、管理者寫入流程、區網連線、長時間成長未驗證。
6. 資料授權僅有使用者聲明（本競賽專題範圍）；Quick Tunnel 只供展示與測試。
